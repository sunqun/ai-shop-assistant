# 商城计价一致性审查

## 输入与边界

输入为仓库路径、要审查的入口或变更范围，以及报告输出位置。缺少范围时，检查当前仓库的网页报价、Agent 报价和下单金额重校验。先读取仓库 `AGENTS.md`，保留用户对测试、支付和数据库操作的限制。

默认只读源码和已有测试，不连接模型或数据库，不执行测试、构建、迁移或真实建单；不为了审查直接修复代码。用户明确要求执行额外操作时，仍遵守其指定范围。

## 审查方法

1. 从 `package.json`、目录和实际导入定位计价函数、报价服务及网页/Agent 入口。不要仅凭文件名或旧文档判断实现已共用。
2. 沿每个入口追踪到实际计算函数，记录文件、函数和当前行号。下单前重新计算是同一实现的复用，不因调用多次就认定存在多份公式。
3. 搜索满减门槛、运费、百分比和金额转换的其他实现；区分业务公式、金额格式化、共享小计工具与测试里的期望常量，不能把每个金额字面量都报成重复实现。
4. 检查金额单位和舍入是否一致，服务端是否决定价格与资格，前端和模型是否仅消费已验证结果。
5. 读取相关用例，指出哪些条件已有断言，哪些只从源码得到支持。源码存在和测试文件存在均不代表已经实际执行通过。

当前 AI 商城可从以下位置开始；若目录已变，沿导入查找新位置，不创建兼容副本：

- `lib/pricing-domain.ts`：价格规则、金额转换和行小计。
- `lib/repository/quote-service.ts`：共用报价服务。
- `lib/repository/order-service.ts`：下单前的规则及金额校验。
- `app/api/v1/carts/quote/route.ts`：网页报价。
- `app/api/v1/assistant/cart/quote/route.ts`、`lib/mcp/commerce-server.ts`：Agent 报价。

## 输出

报告包含审查范围、实际调用链、证据位置、发现的问题及影响、未验证项和后续建议。结论按证据限定，不把不同来源金额不同直接判成错误，也不把当前实现视为业务规则已获批准。

若没有发现重复实现，写明搜索范围和已追踪入口；不要扩大为整个项目所有金额逻辑均经过运行验证。
