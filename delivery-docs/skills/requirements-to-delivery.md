# 需求到交付

这是全局、跨项目 skill。不得假设项目的行业、语言、框架、运行平台、目录结构、部署方式或测试工具。先读取项目自身的规则和现有代码，再采用其中适用的约定。用户明确指令优先于本 skill 的默认工作流。

## 交付流程

必须按以下顺序完成；如果有依赖无法满足，说明阻塞原因，并继续处理不依赖该条件的工作：

1. **读取需求清单**：定位用户指定或项目中已确认的需求清单，读取验收标准、确认记录、待决项和相关技术文档。若没有明确指定文件，先检查项目文档和规则；仍有多个候选时再询问用户。
2. **检查项目上下文**：确认仓库根目录、适用的 `AGENTS.md`、Git 状态和现有改动，了解技术栈、相关实现、依赖、构建方式和测试命令。保留用户已有修改。
3. **确认可实现范围**：把需求逐条映射到代码变更和验收标准。发现未确认、相互冲突或足以改变产品行为的关键规则时，不自行决策；暂停依赖该决定的实现并明确列出所需确认。其余独立部分可继续。
4. **实现代码**：依据确认过的需求和验收标准修改代码，遵循现有架构和约定。优先复用已有能力，避免无关重构；不得静默缩减需求范围或虚构项目能力。
5. **调用 `code-review` skill**：实现后必须调用当前环境可用的 `code-review` skill，对本次实际差异及相关调用路径进行只读审查。处理每项有效发现；若认为某项不适用，记录依据。修复后再次审查受影响的差异，直至没有未处理的有效发现，或明确记录无法处理的原因和风险。
6. **生成测试用例**：根据需求验收标准和 review 发现，编写或更新有意义、可执行的测试用例。优先覆盖用户可见主流程、边界条件、失败处理、权限/安全边界、数据完整性和回归风险；按项目测试体系选择测试层级。测试用例应能追溯到需求条目或验收标准。每次生成或更新测试用例，都必须在项目版本文档目录下新建独立的 case 目录保存本次用例及执行记录，例如 `docs/<version>/cases/<日期>-<主题>/`；目录名称和文件名称使用项目约定，不能覆盖其他批次的用例。
7. **按测试用例再次自检**：逐条执行或验证本次测试用例，检查实际结果与预期结果；同时运行项目中适用的构建、静态检查和回归测试。失败时修复实现或测试问题并重跑受影响用例。环境不允许执行的用例要标明未执行原因，不得报告为通过。
8. **记录改动并交付总结**：每次发生代码改动，都必须在项目文档根目录下新建独立的改动记录目录，优先使用 `docs/changes/<日期>-<主题>/`；如果项目规则明确使用 `doc/`，则使用 `doc/changes/<日期>-<主题>/`。改动记录至少包含改动概要、改动原因/需求来源、改动文件清单、改动时间（含时区）、验证命令及结果、code review 结论和遗留风险。交付总结还要说明需求覆盖、测试用例目录与执行结果、运行过的其他检查，以及涉及文件和仍存在的限制/风险。

## 需求与验收规则

- 以已确认的需求清单和验收标准为实现依据，不把需求文档中的假设自动视为已批准决策。
- 将需求映射到代码、测试和结果；发现缺失、冲突或不可验证的验收标准时，记录问题并请求必要澄清。
- 未确认的授权、隐私、数据保留/删除、资金或其他高影响业务规则均需由用户或批准规格确认。具体领域按当前项目识别，不预设固定领域清单。
- 不记录隐藏的内部思维过程；只记录确认过的决策、可观察理由、证据、测试结果和遗留风险。

## 项目改动边界

- 按用户要求和项目规则确定交付物及允许修改范围。实现请求通常包含必要的源代码、测试和相关文档修改。
- 不因实现授权而推断用户同意生产环境操作、发布、部署、外部通信、破坏性仓库操作或其他未授权的外部影响。
- 若用户要求只分析、只审查或禁止运行命令，遵守该限制，并说明完整交付流程中哪些步骤因此未执行。
- 测试、构建、安装依赖和其他命令必须依据项目实际工具与当前权限执行；不得编造命令或声称未观察到的结果。
- 仅在有助于项目且符合用户要求时创建额外设计文档、测试报告或决策记录，不为小型改动制造无必要的流程产物。

## 推荐调用方式

```text
$requirements-to-delivery
读取已确认的需求清单及其验收标准，按项目约定实现代码；实现后调用 code-review skill 审查，处理发现，再生成测试用例并按用例逐条自检，最后汇总测试与审查结果。遇到未确认的关键产品规则时先列出并暂停依赖它的实现。
```
