# 需求解析与功能模块拆分

这是一个跨项目 skill。不得假设项目属于某个行业、使用某种语言或框架、只支持某种设备，或必须采用某种文档目录。项目规则、用户明确要求和已有代码约定优先；如果项目提供了文档目录、命名规范、测试命令或模块拆分规范，遵循项目规则并在输出中说明采用的规范。

## 触发方式

### “拆分需求”

当用户说“拆分需求”或表达同等意图时：

1. 读取原始需求、适用的 `AGENTS.md`、项目说明、已有需求文档和必要的代码上下文。
2. 区分用户明确提出的内容、基于上下文的假设、可选建议和待确认问题。
3. 生成三份相互关联的文档：
   - 需求功能清单；
   - 前端交互与技术文档；
   - 后端技术文档。
4. 在回复中给出文档路径、需求结论、风险和必须确认的问题。

需求分析阶段默认只修改需求/技术文档和用户明确允许修改的规则文件，不修改业务源代码、数据库迁移、依赖配置、部署配置或测试实现。用户明确要求直接实现时，转入项目规定的实现流程；不要把需求分析默认为编码授权。

### “拆分功能模块”

当用户说“拆分功能模块”或表达同等意图时：

1. 基于已确认需求或当前可用需求，按用户可完成的端到端业务闭环拆分模块。
2. 每个模块必须能独立说明目标、入口、页面/交互、数据变化、接口契约、验收标准和依赖。
3. 为模块生成单独的模块拆分文件；文件名和目录遵循项目规则。没有项目规则时，建议使用 `docs/<version>/module-breakdown.md`，不要覆盖已有文档。
4. 模块拆分应达到便于后续编码的细粒度：任务按可独立修改、可独立验证、风险边界清晰的工作单元划分，避免按“前端/后端/数据库”机械分层，也避免把无法单独验收的零散任务当作模块。
5. 不自动开始实现代码，除非用户同时明确要求实现。拆分文件必须让后续实现、测试和审查可以直接据此执行。

## 三份需求文档的最低内容

### 需求功能清单

至少包含：

- 背景、目标和范围；
- 用户角色、使用场景和前置条件；
- 功能清单及优先级；
- 用户可见行为、系统行为和状态变化；
- 数据、接口、权限和审计要求；
- 非功能需求；
- 可验证的验收标准；
- 冲突、风险、假设和待确认问题。

每条验收标准都必须能通过示例、自动化测试、检查或人工验收判断是否满足，并标明对应功能或模块。

### 前端交互与技术文档

覆盖所有涉及的页面、视图或交互入口。至少包含：

- 页面/路由、页面目的和用户入口；
- 页面布局设计：区域划分、信息顺序、组件位置、主要/次要操作、提醒、费用或状态展示位置；
- 关键页面的文本线框或布局图，明确空间关系；
- 关键用户流程和状态流转，交互图优先使用 Mermaid；
- 客户端状态、数据请求、缓存和 API 消费方式；
- 加载、空数据、失败、权限不足、资源失效和处理中状态；
- 窗口/屏幕尺寸、内容宽度、分栏或栅格、吸顶/固定区域、断点和防遮挡/横向溢出规则。按需求和项目目标选择桌面、移动端或其他终端，不擅自添加未要求的平台；
- 可访问性、错误提示和安全边界；
- 页面行为与后端状态、权限和业务规则的一致性。

交互流程图不能替代页面布局设计。纯后端或无界面需求必须明确标注前端布局不适用的原因，并提供可验证的 API、事件或集成演示方式。

### 后端技术文档

至少包含：

- 服务/模块边界和领域职责；
- 核心实体、数据模型和数据约束；
- API、事件或任务契约，包括输入、输出、错误和幂等性；
- 身份认证、授权、审计和数据访问边界；
- 事务、一致性、并发、重试和补偿策略；
- 同步/异步流程、可靠性和失败处理；
- 性能、容量、观测、告警和安全要求；
- 测试策略、数据准备和验收方式。

涉及支付、订单、库存、费用、授权、隐私、数据删除或其他高影响规则时，未被用户或现有批准规格确认的内容必须标记为 `needs_human_review`，不得擅自写成已批准方案。

## 功能模块拆分文件的最低内容

模块数量由业务闭环、依赖、风险隔离和独立验收需要推导，不使用固定模块数量。每个模块至少包含：

1. **模块身份**：名称、目标、范围、非目标、负责人/所有者（如已知）。
2. **完整链路**：入口、前置条件、主流程、成功结果、失败/取消/重试分支、结束条件。
3. **可查看交互**：页面或视图清单、页面目的、布局/线框、主要操作、状态展示、关键提醒，以及可复现的交互路径。无页面时说明原因并给出 API/事件/命令演示。
4. **契约**：前端与后端接口、事件、数据模型、状态机、权限、错误码、幂等和依赖契约。
5. **验收标准**：与需求功能点和 AC 建立映射，覆盖正常、边界、失败、权限和数据一致性场景。
6. **细粒度实现任务**：按可独立修改和验证的最小合理工作单元排列；每项写清输入、输出、影响文件/边界、依赖、完成条件和验证方式。任务顺序应服务于高效编码，先稳定契约和基础能力，再实现主链路，最后补齐异常、权限、观测和体验细节。
7. **可执行测试用例**：每条包含唯一 ID、目的、前置条件、测试数据、操作步骤、预期结果、清理方式、AC 映射和自动化/手工标记。给出仓库实际可用的测试命令、所需环境和数据准备方式；不能虚构尚未存在的命令。
8. **Code review 清单**：列出审查范围、关键不变量、权限/安全/数据一致性检查、兼容性和回归风险、应查看的文件/接口，以及通过标准。需要执行审查时，给出仓库中实际可用的 review 命令或明确的人工审查步骤。
9. **依赖与交付顺序**：前置模块、可并行任务、阻塞项、跨模块共享契约和独立验收顺序。
10. **状态与遗留风险**：`draft`、`needs_human_review`、`ready`、`in_progress`、`verified` 等状态的含义、当前状态、未决问题和风险。

模块边界必须按用户可完成的纵向链路划分，而不是按技术层拆分。共享领域服务或写入契约只能有明确的单一所有者，避免多个模块重复实现同一核心行为。一个模块只有在页面/API 链路可演示、测试用例可执行、测试结果可记录、review 清单已完成且遗留风险明确后，才能标记为 `verified`；不得用目录、任务标题或未执行的命令代替验证。

## 分析流程

1. **确认上下文**：读取适用规则、需求来源、项目结构、技术栈、现有页面/接口、测试和交付命令。只读取完成判断所需的代码。
2. **提取需求**：把原始文字转换为角色、场景、能力、状态、数据、权限、约束和验收标准。
3. **识别问题**：检查矛盾、遗漏、越权假设、不可验证承诺、金额/数据/权限/隐私风险和非功能目标冲突。
4. **设计确认问题**：按“必须确认、建议确认、可延后”分类；问题必须具体，必要时提供 2 到 3 个方案及影响。
5. **产出文档**：按触发语生成三件套或模块拆分文件；在文档中保留证据、假设、决策理由和版本信息，不写模型内部思维过程。
6. **自检覆盖**：检查需求到页面/接口/状态/测试/验收的映射，检查主要操作可达，检查布局与契约一致，检查所有高影响未决项均已标记。

## 人工确认闸门

存在必须确认的问题时，相关规格保持 `needs_human_review`，明确告知用户尚未进入批准或实现阶段。不得自行补全支付、费用、授权、订单、库存、隐私、数据保留或其他会显著改变产品行为的规则。

用户确认后记录：确认内容、确认上下文、受影响的需求和验收标准、放弃的备选方案及原因、规格版本。只有关键问题已确认，或用户明确授权采用已记录的默认假设，才能标记为 `approved` 或 `ready`。

## 推荐调用方式

```text
$requirements-analysis
拆分需求：读取这份原始需求，生成需求功能清单、前端交互与技术文档、后端技术文档；只修改需求文档，不实现业务代码。
```

```text
$requirements-analysis
拆分功能模块：基于已确认的需求规格生成模块拆分文件。每个模块必须是完整可验收链路，包含可查看交互、前后端契约、细粒度实现任务、可执行测试用例和 code review 清单；不要开始写业务代码。
```
